# MP3 → 文章

两阶段流水线：**转写**（脚本，多文件并行）→ **润色成文**（subagent，多任务并行）。
输出语言与音频语言一致（只润色，不翻译）。

## 阶段 1：转写

对每个音频文件执行（多个文件时用后台任务并行跑）：

```bash
python3 .claude/skills/mp3-to-article/scripts/transcribe.py <音频文件> -o dump/transcripts/<名称>.txt
```

- 默认后端 `glm`（GLM-ASR-2512），需仓库根 `.env` 配置 `GLM_API_KEY`
- 脚本自动切片（16kHz 单声道）处理 API 的 30 秒限制并链式传递上下文，无需干预
- `--backend mlx` 为 Mac 本地方案预留（尚未实现）
- **单文件转写模式**（`--workers`）：
  - 默认 `--workers 1`：串行链式上下文，段边界衔接好、人名术语前后一致（质量优先）
  - `--workers 8`：段级并行无上下文，实测 13 分钟音频 28s → 3s（约 9 倍提速），
    段边界可能丢字/错认人名（实测 97.5% 相似），批量处理大量文件时使用
- **文件之间必须并行调度**（多个后台任务同时跑）

## 批量处理（任意规模，自动调度）

小批量（≤10 个文件）：直接用多个后台任务并行跑 `transcribe.py`（文件间并行、文件内串行链式）。

大批量（>10 个文件）或用户不指定规模时，统一用调度器 —— 它自动处理并行分批、断点续跑、失败隔离，无论输入多大都不会崩：

```bash
python3 .claude/skills/mp3-to-article/scripts/batch.py <音频文件或目录...> -o dump/transcripts
```

调度逻辑（实测依据）：

- **文件级并行 8**：GLM API 加速的饱和点（8 并发 3s vs 32 并发 5s，更高为负优化）
- **单文件内部串行链式**（workers=1）：保段边界衔接与人名一致（质量优先）
- **进程级隔离**：每个文件独立子进程，单文件失败不中断整批
- **断点续跑（幂等）**：输出已存在的自动跳过；中断/失败后重跑同一命令即续补
- 结束打印汇总，失败清单列出；退出码非零代表有失败

## 阶段 2：subagent 润色成文

每个转写稿派一个 subagent（Agent 工具，**每批 ≤10 个并行派发**，上一批完成后再派下一批，直至全部完成），指令要点：

- 通读全文，输出**原语言**的结构化文章（不翻译）
- 去除口语填充词（嗯、呃、就是说、这个那个）和重复表述
- 忠于原意：不新增观点，不删减有信息量的内容
- 修正明显的转写错误（同音字、专有名词，结合上下文判断）
- 组织结构：起一个贴切标题，合理使用小标题分节、分段
- 输出 Markdown，写入 `dump/articles/<名称>.md`（用户指定目录时以用户为准）

## 输出与收尾

- 中间产物（转写稿）在 `dump/transcripts/`，成品文章在 `dump/articles/`，均在 dump/ 下不提交
- 完成后向用户报告每个文件的文章路径和字数
